MOIRAI: A Mathematical Model for Flight-Test Campaign Scheduling and Deadline-Risk Analysis

Greedy block scheduling under regulatory duty limits, with a seasonal weather model and Monte-Carlo risk, sensitivity and resource analysis

Engine specification — Moirai.Core. Fixed-wing, day operations; limits from the FTOM (Table 3, FW column).

Abstract

MOIRAI plans a day-by-day, intra-day-block schedule of sorties (real flights) and rehearsals (simulator sessions) for a set of flight-test campaigns sharing a pool of pilots, flight-test engineers, and aircraft. The scheduler is a deterministic, deadline-ordered, greedy forward pass with no backtracking; every assignment is gated by a precise model of the Flight-Test Operations Manual (FTOM) duty, flight-hour, rest and consecutive-day limits. Operational uncertainty enters through (i) a seasonal, autocorrelated weather model built on a two-state Markov chain, and (ii) a campaign-level test-yield model with an exponential retest learning curve and whole-sortie aborts. A Monte-Carlo layer turns one schedule into a risk profile — deadline-confidence probabilities, completion-date percentiles, and an effort distribution — using common random numbers for variance reduction. On top of it sit a lever-based resource recommender and a one-factor-at-a-time sensitivity analysis. This document specifies the complete mathematical model: notation, the weather and yield processes, the FTOM feasibility predicates, the scheduling algorithm, the program-level verdict, and the analysis layer.

1. Introduction and scope

A flight-test program consists of several campaigns, each a body of test work that must be flown by qualified crews on compatible aircraft, within regulatory duty limits, before a deadline. Two coupled difficulties make manual planning unreliable: the binding resource is rarely obvious (it may be aircraft, crew, weather, or a prerequisite chain), and the weather is both seasonal and streaky, so a single nominal plan systematically overstates confidence. MOIRAI addresses both by separating a fast, deterministic evaluation function — the scheduler — from a stochastic layer that wraps it.

The scope is fixed-wing (FW), day operations, with limits taken from the FTOM Table 3, FW column. The engine is pure: Schedule Run(Scenario) performs no input mutation and no I/O, which is what allows the analysis layer to call it thousands of times on cloned scenarios. Nothing in this section is hard-coded; every constant in Table 1 is data on the scenario.

2. Notation and entities

We resolve all identifiers to integer indices once at the start of a run: persons are indexed \(p\) over the concatenation of pilots then engineers, aircraft (tails) by \(a\), campaigns by \(c\), and calendar days by \(d \in \{0,\dots,H-1\}\), where \(d\) is the offset from the horizon start and \(H\) is the horizon length in days. The block index within a day is \(b \in \{1,\dots,B\}\), where \(B=\)BlocksPerDay.

3. Time and the two availability axes

MOIRAI keeps two independent notions of unavailability, by design, plus two per-resource ones.

  • Workday. A day is a workday iff it is not a weekend and not a holiday: \(\mathrm{work}(d) = \neg\mathrm{weekend}(d)\wedge\neg\mathrm{holiday}(d)\). The administrative calendar owns this.
  • Flyable. A day is operationally flyable (weather/NOTAM) according to a flyable-day model \(\mathrm{fly}(d)\in\{0,1\}\) (Section 4). This is independent of the calendar.
  • Usable. \(\mathrm{usable}(d)=\mathrm{work}(d)\wedge\mathrm{fly}(d)\).
  • Maintenance / leave. Aircraft maintenance \(\mathrm{maint}(a,d)\) and personnel leave \(\mathrm{leave}(p,d)\) are per-resource inclusive date ranges, kept off the calendar/weather axes.

A sortie requires a usable day, an aircraft not in maintenance, and crew not on leave. A rehearsal runs on the simulator, so it requires only a workday (weather-independent) and crew not on leave.

4. The weather model

Flyability is supplied by one of three models. The first two are deterministic; the third is the stochastic model that drives all risk analysis.

4.1 Deterministic rate pattern

Given a rate \(r\in[0,1]\), a pattern length \(\ell\) and an anchor day \(a_0\), the rate-based model is flyable iff the day's position in the repeating pattern falls below a rounded threshold:

\[ \mathrm{pos}(d) = \big((d-a_0)\bmod \ell + \ell\big)\bmod \ell,\qquad \mathrm{fly}(d) = \mathbf{1}\!\left[\,\mathrm{pos}(d) < \operatorname{round}(r\,\ell)\,\right], \tag{1} \]

with round taken half-away-from-zero (matching the MATLAB reference). The realized rate is \(\operatorname{round}(r\ell)/\ell\), so \(\ell\) is chosen to divide the rate evenly when the exact value matters.

4.2 Seasonal probabilistic model

The probabilistic model carries a vector of twelve monthly flyable rates \(r_1,\dots,r_{12}\) (winter low, summer high) and a single persistence parameter \(\varphi\in[0,1)\). For day \(d\) we write \(r \equiv r_{m(d)}\) for the rate of its calendar month.

Its nominal realization — used by an ordinary deterministic run — is the rate pattern of Eq. (1) evaluated with the month rate \(r_{m(d)}\). This makes a normal run use the expected seasonal pattern.

4.3 The two-state Markov chain

A stochastic realization over \([d_0,d_1]\) is drawn from a time-varying two-state Markov chain on \(\{\mathrm F\ (\text{flyable}),\,\mathrm N\ (\text{not})\}\). The first day is a Bernoulli draw \(P(\mathrm F)=r\); thereafter, with the current month rate \(r\),

\[ P(\mathrm F_d \mid \mathrm F_{d-1}) = r + \varphi\,(1-r), \qquad P(\mathrm F_d \mid \mathrm N_{d-1}) = r\,(1-\varphi). \tag{2} \]

Two properties make this the right object. First, the stationary rate is exactly \(r\), for any \(\varphi\). Writing \(\pi\) for the stationary probability of \(\mathrm F\) and solving the balance equation \(\pi = P(\mathrm F\mid\mathrm F)\,\pi + P(\mathrm F\mid\mathrm N)\,(1-\pi)\),

\[ \pi = \frac{r(1-\varphi)}{1-\big[r+\varphi(1-r)\big]+r(1-\varphi)} = \frac{r(1-\varphi)}{1-\varphi} = r . \tag{3} \]

Second, \(\varphi\) is exactly the lag-one autocorrelation of the flyable indicator: the gap between the two transition probabilities,

\[ P(\mathrm F\mid\mathrm F)-P(\mathrm F\mid\mathrm N) = \big[r+\varphi(1-r)\big]-r(1-\varphi) = \varphi . \tag{4} \]

So \(\varphi\) lengthens good and bad spells — it controls streakiness — without changing the long-run flyable fraction. Crucially, since the mean is fixed, \(\varphi\) acts purely on the variance of the number of flyable days available before a deadline: higher \(\varphi\) widens that distribution. The effect on deadline confidence is therefore regime-dependent. A program that is comfortably on track is hurt by streakiness — independent (Bernoulli) days over-state its confidence by ignoring the chance of a long bad spell. A program likely to miss is helped: it needs an above-mean run of flyable days, and a wider distribution puts more probability in that upper tail (“variance helps the underdog”). Both directions are correct; only the mean-fixing property (Eq. 3) is regime-independent. Seasonal \(r_{m}\) then make winter campaigns far more fragile than summer ones.

5. Workload and the test-yield model

5.1 Raw workload

The raw plan is purely combinatorial: a campaign needs

\[ S_c = \left\lceil \frac{\mathrm{TTP}_c}{\mathrm{TPS}_c} \right\rceil \tag{5} \]

sorties, each flying \(\min(\mathrm{TPS}_c,\ \text{remaining})\) test points. With the test-efficiency switch off (the default), this is the exact behaviour and the parameters below are ignored.

5.2 Retest learning curve

Not every attempted point holds: data may come back unusable, or the point falls outside its tolerance band and must be re-flown. The probability that a point requires a retest decays with experience, measured in good (valid) points accumulated, \(g\):

\[ p_c(g) = f_c + (s_c - f_c)\,e^{-g/\lambda_c}, \tag{6} \]

where \(s_c\) is the start probability, \(f_c \le s_c\) the maturity floor, and \(\lambda_c\) the learning scale (CL1 Test points to mature). With \(\lambda_c \le 0\) the rate is constant at \(s_c\). A demanding discipline (e.g. flutter) starts high and matures slowly; routine performance work starts low.

5.3 Stochastic yield of one sortie

A sortie attempting \(a\) points first draws a whole-sortie abort with probability \(\alpha_c\) (or a scenario-wide override). An aborted sortie makes zero progress but still consumes the day's resources. Otherwise each attempted point is held independently with probability \(1-p_c(g)\), the retest probability being evaluated at the campaign's current CL1 Test point count:

\[ \text{CL1 Test points} \;=\; \begin{cases} 0, & \text{w.p. } \alpha_c\ \ (\text{abort}),\\[2pt] \displaystyle\sum_{i=1}^{a}\mathbf{1}\!\left[U_i \ge p_c(g)\right], & \text{otherwise}, \end{cases} \tag{7} \]

with \(U_i\sim\mathcal U(0,1)\). All randomness enters through one injected stream per realization, which is what lets the analysis layer reproduce any run exactly.

5.4 Expected workload inflation

For planning and for the deterministic "expected vs. raw sorties" preview, the mean retest probability over the campaign's planned points is the analytic average of Eq. (6) over \([0,N]\) with \(N=\mathrm{TTP}_c\):

\[ \bar p_c = f_c + (s_c-f_c)\,\frac{\lambda_c}{N}\Big(1-e^{-N/\lambda_c}\Big). \tag{8} \]

Each non-aborted sortie then yields a fraction \((1-\bar p_c)\) of its attempted points, and a fraction \((1-\alpha_c)\) of sorties are non-aborted, so the expected number of sorties scales by the reciprocal of their product — the workload inflation

\[ I_c = \frac{1}{(1-\bar p_c)\,(1-\alpha_c)} \;\ge\; 1 . \tag{9} \]

The expected sortie count is \(\big\lceil \mathrm{TTP}_c\, I_c / \mathrm{TPS}_c\big\rceil\); under losses the realized count is a random variable, which is why the risk layer reports a distribution rather than a single number.

6. Regulatory feasibility (FTOM)

Every tentative assignment is checked against the FTOM limits. Define the rolling window sum of a per-person series \(x_{p,\cdot}\) ending on day \(d\),

\[ W(x_p,d,w) = \sum_{k=\max(0,\,d-w+1)}^{d} x_{p,k}, \qquad Y(x_p,d) = \sum_{k:\,\mathrm{year}(k)=\mathrm{year}(d)} x_{p,k}, \tag{10} \]

where \(Y\) is the calendar-year sum. Leave and block-occupancy are not checked here — they are day-grid facts ANDed in at the call site — so these predicates concern hours only.

6.1 Sortie eligibility

A person \(p\) may take a sortie on day \(d\) adding \((\Delta\phi,\Delta\delta,\Delta\delta^{\mathrm{fd}})\) iff all of the following hold (the engine short-circuits on the first violation):

\[ \begin{aligned} &n^{\mathrm s}_{p,d} < N^{\mathrm s}_{\max}, \qquad c_{p,d} < C_{\max}\ \ (\text{rule 19}),\\[4pt] &x^{\mathrm f}_{p,d}+\Delta\phi \le F_1,\quad W(x^{\mathrm f}_p,d,7)+\Delta\phi \le F_7,\\ &W(x^{\mathrm f}_p,d,28)+\Delta\phi \le F_{28},\quad Y(x^{\mathrm f}_p,d)+\Delta\phi \le F_y,\\[4pt] &x^{\mathrm d}_{p,d}+\Delta\delta \le D_1,\quad W(x^{\mathrm d}_p,d,7)+\Delta\delta \le D_7,\\ &W(x^{\mathrm d}_p,d,14)+\Delta\delta \le D_{14},\quad W(x^{\mathrm d}_p,d,28)+\Delta\delta \le D_{28},\\[4pt] &\textsc{rest}(p,d,\Delta\delta),\qquad \big[\,\text{if } D^{\mathrm{fd}}<\infty:\ x^{\mathrm{fd}}_{p,d}+\Delta\delta^{\mathrm{fd}}\le D^{\mathrm{fd}}\,\big]. \end{aligned} \tag{11} \]

Here \(c_{p,d}\) is the number of consecutive prior days on which \(p\) flew (\(x^{\mathrm f}>0\)), counted back to the first gap — this is FTOM rule 19. The flight-duty cap \(D^{\mathrm{fd}}\) is optional (default \(+\infty\), i.e. disabled).

6.2 The rest rule

Rest is modelled at day granularity from a common notional daily start, so the rest between two consecutive duty days \((a,a{+}1)\) is \(24-\mathrm{duty}(a)\). Adding \(\Delta\delta\) of duty to day \(d\) is rest-feasible iff neither adjacent duty day is over-run:

\[ \textsc{rest}(p,d,\Delta\delta):\quad \begin{cases} x^{\mathrm d}_{p,d-1} > 0 \;\Rightarrow\; 24 - x^{\mathrm d}_{p,d-1} \ge R_{\min},\\[3pt] x^{\mathrm d}_{p,d+1} > 0 \;\Rightarrow\; 24 - \big(x^{\mathrm d}_{p,d}+\Delta\delta\big) \ge R_{\min}. \end{cases} \tag{12} \]

A duty day longer than \(24-R_{\min}\) hours therefore forbids duty on the adjacent day for that person.

6.3 Rehearsal eligibility

A rehearsal adds duty only (no flight, no flying day, so it never affects rule 19). Person \(p\) may rehearse on day \(d\) adding \(\rho\) duty iff

\[ n^{\mathrm r}_{p,d} < N^{\mathrm r}_{\max},\quad \big(\text{duty windows of Eq. 11 with }\Delta\delta=\rho\big),\quad \textsc{rest}(p,d,\rho). \tag{13} \]

7. The scheduling algorithm

The scheduler is a deterministic, deadline-ordered, greedy forward pass with intra-day block placement and no backtracking. It is the evaluation function that the stochastic layer wraps. State is index-based: per-person ledgers (Section 6), a per-day aircraft block grid, and a cross-day crew-block occupancy tensor \(\mathrm{busy}[p,b,d]\in\{0,1\}\). The cross-day form is required because a rehearsal lands on a past day, so the engine must know which blocks that crew already used there.

7.1 Aircraft vs. crew occupancy

A sortie starting in block \(b\) on aircraft \(a\) occupies the contiguous span \([b,\,b+\beta_c-1]\) on the aircraft (flight plus turnaround), but the crew occupies only the flight block \(b\). Hence a flutter sortie (\(\beta_c=B\)) ties up the tail for the whole day yet leaves its crew free in the other blocks.

7.2 The day loop

for each day d = 0 .. H-1: usable ← work(d) ∧ fly(d) build OPEN = { c : c still needs sorties, StartDate_c ≤ d } if a prerequisite of c is unfinished → tally Prereq, skip c else if not usable → tally NotUsable, skip c sort OPEN ascending by TargetEndDate (then master deadline) repeat (multi-pass; stop when a full pass places nothing): for each c in OPEN still needing sorties: (a) cands ← OrderedAircraft(compatible, not-in-maint(d), least-used, single-tail lock) (a*, b) ← FindSlot(cands, AllowedBlocks_c, β_c) else → reason=Aircraft (b) pilot ← argmin_{eligible} RecentDuty else → reason=Pilot (c) engineers ← E least-loaded eligible else → reason=Engineer (d) tentatively AddSortie(crew, d) (e) find rehearsal day k by walking back ≤ g working days, with a crew-common free block; else rollback → reason=Rehearsal (f) commit: occupy aircraft span, flight block (d), rehearsal block (k); record sortie & rehearsal; update test points / done sorties for each c in OPEN with 0 placements today: tally reason[c]

"Eligible" in steps (b)–(c) means: assigned to the campaign, not on leave on day \(d\), the flight block free in \(\mathrm{busy}\), and the FTOM predicate of Eq. (11) satisfied. A sortie flies \(\min(\mathrm{TPS}_c,\text{remaining})\) test points; when the last is flown the campaign's completion date is set. The multi-pass lets one campaign fly up to \(B\) sorties on a single day (one per block) when resources allow.

7.3 Rehearsal placement

Each sortie requires exactly one rehearsal by the same crew, on a working day within \(g\) working days before the flight (non-workdays are skipped and do not count toward the gap). The rehearsal takes a crew-common free block on its own day — chosen independently of the flight block, which lies on a different day — subject to Eq. (13).

8. Crew and aircraft selection

8.1 Weekly load balancing

Among eligible candidates the engine picks the least-loaded by recent duty over a rolling window, not lifetime duty:

\[ \text{pick } \arg\min_{p\ \text{eligible}} \; W\big(x^{\mathrm d}_p,\,d,\,L\big),\qquad L=\text{LoadBalanceWindowDays (default 7).} \tag{14} \]

The rolling window is deliberate: with lifetime load, a finished earlier campaign's hours bias the balancer to dump a later campaign onto one fresh person until they "catch up". A weekly window spreads work evenly within each week and stops past campaigns from skewing today's choice. Ties are broken by a stable sort; the pilot takes one slot, engineers the \(E\) least-loaded.

8.2 Aircraft policy and geometry

Aircraft choice splits into policy and geometry. The policy orders the compatible tails by least cumulative use (fleet balancing), drops tails in maintenance that day, and — in single-aircraft mode — restricts to the locked tail once the campaign has started flying. The geometry (FindSlot) returns the first \((\text{tail},b)\) whose \(\beta_c\)-block span starts at an allowed block and is entirely free. In single-aircraft mode the campaign waits when its tail is busy or in maintenance — an intentional data-consistency signal rather than a silent fallback.

9. The program-level verdict

Let the schedule's program finish be the latest scheduled sortie date,

\[ T = \max_{s\in\text{sorties}} \mathrm{date}(s)\qquad(\text{undefined if nothing flew}). \tag{15} \]

Campaign \(c\) completes when it reaches \(S_c\) sorties; its completion date \(T_c\) is the date of that last sortie. A soft milestone is met iff \(c\) completes and \(T_c \le \tau_c\), its target date. The program is delivered iff every campaign completes and, when a master deadline \(M\) is set, the finish is within it:

\[ \mathrm{Delivered} \;\Longleftrightarrow\; \Big(\textstyle\bigwedge_c \text{complete}(c)\Big)\ \wedge\ \big(M=\varnothing \ \vee\ T \le M\big), \qquad \mathrm{slack} = M - T . \tag{16} \]

Campaign targets \(\tau_c\) are soft internal milestones: they drive scheduling order and the met/missed report, but missing one is not program failure. The binding date is the master deadline.

10. Bottleneck analysis

Diagnosis is a by-product of the day loop. Whenever an open, usable campaign places zero sorties on a day, the engine records the dominant blocking reason for that day in one of six per-campaign counters:

\[ \text{reason} \in \{\textsf{Prereq},\ \textsf{NotUsable},\ \textsf{Aircraft},\ \textsf{Pilot},\ \textsf{Engineer},\ \textsf{Rehearsal}\}. \]

The dominant counter explains why a campaign slipped — e.g. "dominant bottleneck = aircraft (13 days)" — and it gates the resource recommender so that it does not propose crew when the binding constraint is weather or a prerequisite.

11. Monte-Carlo deadline-risk analysis

A single deterministic schedule understates risk. The Monte-Carlo layer turns the scenario into a risk profile by running the scheduler over \(N\) sampled realizations. A realization \(k\) carries a weather sample \(\mathrm{fly}^{(k)}\) from the Markov chain (Section 4.3) and a yield stream from Section 5.3; the scheduler runs on a scenario clone with that weather and yield, the engine being pure.

11.1 Aggregates

Let \(\mathcal D_c^{(k)}\) be the completion day of campaign \(c\) in run \(k\) (absent if it did not finish). The reported quantities are

\[ \hat P(\text{meet}_c) = \frac1N\sum_{k=1}^N \mathbf 1\!\left[T_c^{(k)}\le\tau_c\right],\qquad \hat P(\text{delivery}) = \frac1N\sum_{k=1}^N \mathbf 1\!\left[\mathrm{Delivered}^{(k)}\right], \tag{17} \]

together with \(\hat P(\text{incomplete}_c)\), the program-finish distribution, and an effort distribution (mean and percentiles of the sortie count, plus the mean aborted-sortie count). Completion-date and finish percentiles use the nearest-rank rule over the \(N'\) runs that finished: sort the valid days and take index \(\operatorname{clamp}(\lceil qN'\rceil-1,\,0,\,N'-1)\) for quantile \(q\in\{0.1,0.5,0.9\}\). Each percentile retains the index of a realizing run, so its exact schedule can be replayed and drawn.

11.2 Common random numbers

To compare candidate scenarios fairly and reduce variance, every evaluation uses the same per-run randomness. Run \(k\) is seeded by a SplitMix-style avalanche of the base seed and \(k\),

\[ \textsc{mix}(\sigma,k):\quad z \leftarrow \sigma + k\cdot\texttt{0x9E3779B9};\quad z \leftarrow \big((z\oplus z{\gg}16)\cdot c_1\big);\ \dots\ \Rightarrow\ \text{seed}_k, \tag{18} \]

so any two candidates face identical weather and yield streams at each \(k\). The same seed reproduces the same realization, which underlies the replay feature. Runs execute in parallel on per-thread clones; the seed is fixed (not a UI knob) so results are reproducible — one increases \(N\) for accuracy, not changes the seed.

11.3 Risk decomposition

Running the same \(N\) seeds three times — weather varying with lossless yield, yield varying with the nominal weather pattern, and both together — isolates the driver of risk. Because the seeds match, the differences are signal, not noise. A low single-source \(\hat P(\text{delivery})\) means that source alone can blow the deadline; if the yield-only number is low even under perfect (nominal) weather, test efficiency is the dominant driver.

12. Resource recommendation

The recommender is a greedy hill-climb over levers, scored by Monte-Carlo confidence under common random numbers. The score is the expected number of campaigns meeting their target,

\[ \Phi(\text{scenario}) = \sum_c \hat P(\text{meet}_c), \tag{19} \]

evaluated against the same \(N\) realizations for every candidate. At each step the search tries one candidate per enabled lever — add a pilot / engineer / aircraft (assigned to failing campaigns), reassign an existing crew member, loosen a daily limit (\(N^{\mathrm s}_{\max}\!+\!1\) or \(B\!+\!1\)), raise a campaign's test-points-per-sortie (fewer required sorties), improve its retest rate, or reduce its aborts — keeps the best improving move, and stops when every campaign reaches the target confidence or nothing helps. Gating on the bottleneck of Section 10 keeps it from recommending hardware for a weather- or prerequisite-bound campaign; in that honest case it reports the structural limit instead.

13. Sensitivity analysis

Where the risk layer asks "how confident are we?", the sensitivity layer asks "how much does that confidence depend on the parameters we guessed?". It is a one-factor-at-a-time (OFAT) sweep: each model parameter \(\theta\) is perturbed to a low setting \(\theta^-\) and a high setting \(\theta^+\) on a clone, others held at baseline, and the full Monte-Carlo of Section 11 is re-run at the same seeds. The parameter's influence is the swing it induces in the program confidence,

\[ \mathrm{swing}(\theta) = \big|\,\hat P(\text{program};\theta^{+}) - \hat P(\text{program};\theta^{-})\,\big|. \tag{20} \]

The swept parameters and their brackets are: weather persistence \(\varphi \pm 0.2\); flyable rate \(\times\{0.85,1.15\}\); and, when test efficiency is active, abort probability \(\times\{0.5,1.5\}\) and retest probability \(\times\{0.75,1.25\}\). Results are drawn as a tornado — one horizontal bar per parameter, sorted by descending swing, spanning the \(\hat P(\text{program})\) it produces at each end, with segments below the baseline (worse) and above it (better) coloured distinctly. A dedicated sweep over \(\varphi\in\{0.2,0.5,0.8,0.95\}\) reports \(\hat P(\text{program})\) and the median finish at each value, answering the specific "how much does \(\varphi\) matter?" question. Common random numbers guarantee that bar lengths reflect parameter influence, not sampling noise.

14. Discussion: key invariants

The model's coherence rests on a few deliberate choices. The two non-flyable axes (administrative calendar vs. operational weather) are kept distinct, with maintenance and leave as separate per-resource unavailabilities. The engine is pure and greedy with no backtracking, which trades global optimality for a fast, repeatable evaluation function — the natural object for a future optimizer to wrap, in expectation, via the Monte-Carlo layer. The aircraft occupies its block span while the crew occupies only the flight block, decoupling turnaround from crew availability. Load balancing is weekly, not lifetime. And every constant is scenario data, so the same engine serves any FTOM column or operating concept.

The stochastic layer is built on one principle: preserve the mean, model the dependence. The Markov chain keeps the seasonal flyable rate \(r\) exactly (Eq. 3) while letting \(\varphi\) lengthen weather spells (Eq. 4); the yield model keeps the planned test points while letting retests and aborts inflate the work (Eq. 9). Common random numbers then make every comparison — candidate resources, uncertainty sources, parameter perturbations — a fair one. The result is a tool that not only schedules, but explains why a plan slips, how likely it is to hold, and which assumption to firm up first.
